# 已决定事项的落实进度 v1

## 用户可以怎样理解

“已决定”代表意见已经收到；“落实进度”回答谁负责、已经做了什么、下一步及卡在哪里。两者分别记录。

- Codex：协调、检查实现、运行测试及验证手机发布。
- Claude：核对来源、分析差异、提出具体规则建议。
- Wu：只决定尚未批准的实质分类／风险政策。原来的采纳意见无需重复提交。
- 金融账户始终只读。本流程不会执行交易或资金操作。

“已决定 · 落实进度 X 项”整组默认折叠。打开后，每项显示简短标题、进度和一句说明；负责人、下一步、依据及原决定均可再展开。同一报告刷新保留已展开状态，新报告重新默认收起；打印时暂时展开，结束后恢复。

确实需要 Wu 确认或处理的后续事项，在折叠标题旁显示琥珀色“⚠ 待你确认 X 项／待你处理 X 项”，待办页签同时显示提示符。颜色搭配文字，不以颜色作为唯一提示。原“待决定事项”与后续落实请求分别计数；技术处理中或技术受阻不计作用户待办。当前没有此类请求时不显示提示，不制造假待办。

新金融报告未复核旧证据时，显示“历史进度 · 本期尚未复核”，折叠标题显示灰色“历史进度待复核”，不计入本期用户请求。进度读取失败显示“进度未核实”，不误报零项或保留旧版待确认计数。目标复核时间是工作计划，不是假称已有自动任务。

## 维护者执行契约

1. `xuan-ib/implementation-progress.json` 是独立 main 维护账本；既有 events 永不改写或删除，新增事件并提高 revision。改正历史错误也用追加事件。
2. 事件绑定决定 ID、真实 accepted/modified 回执 ID 及该回执原 sourceSha/htmlBlob。`observedPair` 另记核对时报告配对；二者不得混用。证据仅能支持它实际核对的范围。
3. 状态独立于 decision：not_started、in_progress、blocked、awaiting_approval、user_action_required、evidence_recorded。`awaiting_approval` 仅用于尚未批准的后续规则确认；`user_action_required` 仅用于已核实必须由用户处理的明确动作（例如本人登录、补原始资料），必须填写阻碍及具体下一步。不能从 owner、blocker 或自由文本中的“Wu／待处理”猜测状态；不能把技术错误转嫁给用户。没有自动 completed/closed；临时措施有依据，不代表整个后续工作结束。
4. 公开说明仅放必要短文本，不放密钥、联系人、账户号、任意 URL 或原始私人意见。逐仓取数原件留在私有审计目录，禁止随进度发布。
5. 手动维护先跑 `node scripts/xuan-ib-progress.mjs <base-full-sha>` 及测试，再走 exact-SHA OWNER 审批的正常维护 PR。禁止关闭保护、改写原回执、直接修 latest.html/meta。
6. 普通 AM/PM/ad hoc 报告应读取本文件及进度，避免重复要求用户裁决旧事项；继续继承原 decision/receipt 历史。候选依然只允许报告 index.html 一个文件，不能覆盖进度账本。
7. 在新报告证明工作进一步生效后，通过独立维护 PR 追加真实证据事件；不得把调度器成功、聊天声称完成或旧版证据当成本期验收。
8. 主页面独立、无凭据读取进度；same-blob 刷新仍更新；失败不拖垮报告。HTTPS 和受保护 PR 提供发布来源约束；本地 digest 仅用于变更检测，不声称独立数字签名。
9. 手机仅统计已通过账本验证、绑定该事项最新真实回执、且 observedPair 与当前报告精确匹配的后续用户请求。新报告与旧证据不匹配时不宣称当前请求；应由维护者重新核对并追加事件。界面修改不新增请求、不改旧决定/回执/金融金额；任何请求均不是交易授权。
